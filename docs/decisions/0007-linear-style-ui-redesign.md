# ADR-0007 — Linear-Style UI Redesign

**Date**: 2026-03-15
**Status**: Implemented
**Branch**: `feature/multi-agent-tailoring`

---

## Context

The original job list UI was a paginated card-based layout with badge verdicts and `alert()` dialogs for notifications. As job volume grew, pagination became friction-heavy and the visual hierarchy gave no at-a-glance sense of which jobs deserved attention. The design decision session produced a detailed brief targeting a Linear/Vercel minimal SaaS aesthetic — compact rows, actionability-first sorting, and an information-dense detail pane.

Key motivations:
- Pagination forced mental context-switching between pages; infinite scroll keeps focus in one place
- Badge-per-job layout wasted vertical space — users could see ~8 jobs at once instead of 15–20
- `alert()` dialogs blocked the UI and felt jarring for non-critical feedback
- No visual hierarchy: "Apply now" and "Skip" jobs looked identical, forcing users to read every row
- Recruiter contact info (newly captured as `recruiter_email`) had no dedicated surface in the UI
- The detail view showed raw evaluation JSON fields with no storytelling or action affordance

---

## Decision

Replace the entire job list and detail view with a new minimal design. Implement across three commits:

1. **`feat(ui)`** — frontend-only: new components, App.tsx wiring
2. **`feat(eval)`** — backend: `wit_line` field, schema, migration

---

## Implementation

### Job List Panel (`JobListPanel.tsx`)

**Actionability sort** — jobs are sorted by `recommended_action` priority before rendering:

```
apply (0) → tailor (1) → pending (2) → skip (3)
```

Within each tier, sorted by `job_match_score` descending. Sticky section headers with colored dot indicators (green / amber / grey / light-grey) let users scan by tier at a glance.

**Infinite scroll** replaces `<Pagination>`. An `IntersectionObserver` on a sentinel `<div>` at the bottom of the list calls `loadMore()` when it enters the viewport. `useJobs` was refactored to accumulate pages rather than replace them, with stale-request cancellation via a `requestId` ref.

**Recruiter contact modal** — a pill button in the list header shows a count of jobs with known recruiter emails. Clicking opens a modal listing each job/company/email with a toggleable New/Done state (persisted in component state for the session).

**Select-all semantics** — `checked` is computed against `jobs.length` (loaded items) rather than `totalJobs` (API total), since items beyond the current scroll position haven't loaded yet and can't be selected.

### Job List Item (`JobListItem.tsx`)

- 3px colored left edge accent (green/amber/transparent) instead of badges
- Gradient wash `from-green-50/40` or `from-amber-50/40` for apply/tailor rows
- Skip rows rendered at 40% opacity
- Right column: score + verdict label (not badge) + amber recruiter dot
- No border-radius on the row itself — full-width flush rows feel denser

### Job Detail View (`JobDetailView.tsx`)

Full rewrite with embedded sub-components:

**`StepIndicator`** — four-dot pipeline visualizing `applied → screen → interview → offer` states. Dots progress from filled-slate (complete) → amber (current) → outlined (future).

**`ActionRow`** — state machine driven by `recommended_action`:
- `tailor` → "Tailor resume" primary CTA + "Apply anyway" secondary
- `apply` → "Apply now" green primary + "Save for later"
- `skip` → muted "Skip" action
- `applied` → "Applied" confirmation state with interview prep link
- `interview` → interview prep surface

**`KeywordsSection`** — two-column ratio bar showing matched vs missing keywords. Amber chips = "Already yours", blue chips = "Room to grow". Bar width derived from `matched / total` ratio.

**`GapFixRow`** — each gap/improvement rendered as an accordion row. "AI fix ↓" badge expands to show the specific resume edit suggestion. "Prep ↓" badge expands to show interview prep guidance.

**`DynamicSection`** — wires the "Tailor resume ↗" CTA button to the parent's `handleTailor` via an `onTailor: () => void` prop.

**`wit_line`** — a 3–5 word quip generated by the evaluator LLM, shown under the job title as a punchy one-liner (e.g. "Exactly your stack", "Worth the stretch"). Client-side fallback derives the line from `recommended_action` + `job_match_score` if the field is null.

### Toast (`Toast.tsx`)

Shared inline toast component replacing all `alert()` calls in `App.tsx`. Positioned `fixed bottom-6 left-1/2` with slide-in-from-bottom animation. Auto-dismisses after 4.5s. Used for import success/error and batch job feedback.

### `useJobs` Hook Refactor

- Internal `fetchPage(page)` helper preserves existing eval-strategy vs jobs-strategy routing
- `load(page, silent, replace)` with `requestId` stale-request cancellation
- `loadMore()` increments page and appends with deduplication by `id`
- Returns: `jobs, stats, totalJobs, loading, loadingMore, error, hasMore, loadMore, refresh`

### `wit_line` Field (Backend)

- Added to evaluator JSON schema prompt as: `"wit_line": "3–5 word punchy quip about this role"`
- `save_evaluation()` persists it (null if empty string)
- `EvaluationResult` Pydantic schema exposes it
- `apiClient.ts` `Evaluation` interface typed as `wit_line?: string | null`
- Migration `009_add_wit_line.sql`: `ADD COLUMN IF NOT EXISTS wit_line TEXT` + JSONB backfill

## Consequences

**Positive**:
- Jobs sorted by actionability on load — highest-signal work is always at the top
- ~2× more jobs visible per screen height vs card layout
- Recruiter contacts surfaced in a dedicated modal rather than buried in details
- No more `alert()` dialogs blocking the UI
- `wit_line` adds micro-copy personality to evaluation output

**Negative / Trade-offs**:
- `wit_line` will be NULL for all existing evaluations until they are re-evaluated (expected — it wasn't in the prompt before)
- `recruiter_email` NULLs on rows evaluated before the column existed; will backfill naturally on re-evaluation
- The new `JobDetailView` is a larger component (~500 lines) with embedded sub-components — if sub-components grow significantly, they should be extracted to separate files

---

## Note on Branch Strategy

This UI redesign was implemented directly on `feature/multi-agent-tailoring` rather than a separate branch. For future large visual changes, a dedicated UI branch (e.g. `feature/ui-v2`) with a PR that can be reviewed visually before merge is preferred.
